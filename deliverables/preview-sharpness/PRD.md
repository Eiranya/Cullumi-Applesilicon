## 1. 产品定义

### 1.1 产品目标（一句话，可衡量）

> 在参考显示环境（3440×1440、DPR=1、视口 1212px）下，让照片库卡片缩略图的**服务端供给尺寸精确等于卡片图片框的设备像素尺寸**，使屏上清晰度相比**真实旧链路（供 512）提升 ≥ 7%（真实 WebKit 实测 +31.3%）**，同时保真度（MSE↓理想）相比真实旧链路 **改善 ≥ 3×（实测 3.4×）**，且不触碰 512px 分析缩略图与 NIQE 基线。

### 1.2 问题定位（已实测，非假设）

当前不是「像素不够」，而是**供给尺寸与显示框对不上**：

- 卡片图片框实测 215.19×161.39 CSS px，内容区 = **215×143 设备像素**（DPR=1）。
- 磁盘上发布的缩略图长边恒为 **512px**（`cullumi/media.py:analyze_photo()`，`preview.thumbnail((512,512))` → JPEG q86 4:2:0）。
- 浏览器被迫把 512px 缩进 215px 盒，**下采样倍率 2.38**，且 WebKit 用的是 BICUBIC 级滤波器，**约 87% 的锐度损失发生在这一步**（理论 2355.0 → 屏上 1876.4，其中浏览器缩放占 −418.2，即 17.8%）。
- 已排除：源图不足（694 张全部 32.741 MP）、512 上限太小（512 vs 2048 屏上只差 0.05%）、JPEG 质量/采样（q86 4:2:0 → q95 4:4:4 屏上只差 0.09%）。
- 决定性实测（供给侧 A/B）：**倍率 1.00 时两个指标同时最优**——DPR=1 供给 215px，清晰度 +11.5%、保真度 39 倍（MSE 0.54 vs 20.85）；DPR=2 供给 430px，清晰度 +23.9%、保真度 7.4 倍。（原因：倍率 1.00 时浏览器完全不重采样，直接绕开它那个较差滤波器。）

> **落地口径提示**：以上是本环节的**根因排查**（供给侧 A/B，基于「从原图派生的理想供给」）。实际交付链路出于成本考虑**从 512 中间层派生**（不解码原图，HEIC 单张 1655ms），因此真实 WebKit 实测值与上述理想值不同——**验收一律以 §2.2 的真实链路实测为准**。

### 1.3 用户故事

1. **As a** 使用 3440×1440 显示器（DPR=1）的普通用户，**I want** 卡片缩略图在屏幕上呈现它本该有的锐度，**so that** 我判断「这张糊了、该删」时，看到的是照片本身的画质而不是渲染器造成的发虚。
2. **As a** 需要大屏逐张筛查的摄影师用户，**I want** 在不放大、不点开的前提下就能分辨细节与轻微失焦，**so that** 筛选决策不发虚效果误导、不误删。
3. **As a** 使用 Retina/HiDPI（DPR=2）外接屏的用户，**I want** 卡片在 2 倍屏上同样精确匹配、不浪费带宽，**so that** 缩略图网格在任意 DPR 下都清晰且加载更快。

## 2. 技术规范

### 2.1 Requirements Pool

#### P0 —— 必须做（Must have）

| 编号 | 需求 | 说明 |
|---|---|---|
| **P0-1** | **让卡片图片框尺寸可预测（固定、整数 CSS px）** | 当前 `web/css/base.css:411 .gallery { grid-template-columns: repeat(auto-fill, minmax(210px,1fr)) }` 经 `1fr` 分摊后列宽随窗口变化（默认窗口 218.33px / 1212px 视口 215.19px / 最大化 ~221px），无法据此供给固定尺寸。必须改为**确定性固定列宽**（推荐 `repeat(auto-fill, 215px)` + `justify-content: space-between`，空隙吸收余量），使图片框恒为 **213 CSS px**（固定列宽 215px − 卡片 2×1px 边框；推导见本节末尾小注）。这是本需求的前置条件。 |
| **P0-2** | **新增独立「显示用资产」链路，按显示框尺寸精确供给** | 供给尺寸 = 图片框 CSS px × DPR，且**正好等于**（倍率 1.00）。DPR=1 供给 **213 设备像素**。与现有 512px 分析缩略图**分开存储、分开生成**（不得复用同一文件）。 |
| **P0-3** | **严格禁止非整数倍率** | 供给尺寸必须是「精确匹配」，不是「差不多」。**本轮实测反例：供给 214px（= 213+1，仅差 1px、倍率看似 1.00）等非整数倍率场景必须被拒绝；线上必须命中 213 分支。**（历史旁证：早期按 215 口径排查时，供给 216px（=215+1）会使 lapvar 掉到 812、比 215px 低 **40%**——非整数倍率会触发浏览器中间相位重采样。）实现须以「取整后供给尺寸 == 取整后显示框设备像素」作为断言。 |
| **P0-4** | **不得改动现有 512px 分析缩略图及其指纹** | 512 缩略图同时是 NIQE 与 sharpness 指标的输入，参与 `analysis_version()` 缓存指纹（`rgb512-v1` / `raw-preview512-v2`）与 `NIQE_VERSION` 基线。改动会触发全库重新分析并使既有 NIQE 黄金基线失效。**本需求一律不碰它。** |
| **P0-5** | **零回归：任何一张卡片的屏上清晰度不得低于当前基线** | 必须防止「做错方向让观感变差」。实测反例：粒度粗的 `srcset`（只有 256/512 候选）会让浏览器挑 256（倍率 1.19），清晰度 1091.8 **反而低于**当前 512 的 1216.5（该组数字来自早期按 215 口径的供给侧排查，结论方向不变）。 |

#### P1 —— 应该做（Should have）

| 编号 | 需求 | 说明 |
|---|---|---|
| **P1-1** | **支持 DPR=2（HiDPI）精确供给** | 同一固定框在 DPR=2 时供给 **426 设备像素**（= 213×2，倍率 1.00）。实测收益（真实 WebKit）：清晰度 **+41.6%**（lapvar **640.6** vs 真实旧链路 452.4）、保真度 **MSE 10.19 vs 11.88**。须由前端按 `devicePixelRatio` 选择供给尺寸，且同 P0-3 一样要求整数精确匹配。 |
| **P1-2** | **卡片缩略图加载体积不得增加** | 供 213px 替代 512px，像素面积降至约 17.3%，预期同图传输字节数明显下降。验收口径见 §2.2 表（**注意 C1 已收窄为「横构图不高于旧基线」；竖构图 + DPR=2 为已知限制**）。这是一项附带收益，但**属于可量化门槛**（不得回退）。 |
| **P1-3** | **显示用资产可被安全清理与复用** | 新资产需有稳定的缓存键（沿用 `display_preview_path()` 那套「源文件 size:mtime 指纹」思路），源文件更新后旧文件可回收，避免磁盘泄漏。 |

#### P2 —— 可做（Nice to have）

| 编号 | 需求 | 说明 |
|---|---|---|
| **P2-1** | **尺寸定义的单一事实来源** | 固定框尺寸（**213**）目前会同时出现在 CSS 与前端/后端请求逻辑里。应集中为 1 处常量（如 CSS 自定义属性 + 一个 JS 常量），避免后续两处漂移。 |
| **P2-2** | **`srcset` + `sizes` 交给浏览器挑（仅在 P0-1 保证尺寸可预测之后）** | 形如 `srcset="…&w=213 213w, …&w=426 426w, …&w=512 512w" sizes="213px"`。**前提是候选阶梯足够细**；不得只做粗粒度阶梯（见 P0-5）。 |
| **P2-3** | **`image-rendering` 决策记录（默认保持 `auto`）** | `-webkit-optimize-contrast` 能把屏上 lapvar 从 1163.0 拉到 2444.9，但实测等效**最近邻**，MSE↓理想 23.19→45.45、边缘过冲 1.03→3.42，**是走样不是还原**。本需求默认不改。若未来要改，须单独评估并记录取舍。`image-rendering: high-quality` 在 WebKit 实测无效，不要用。 |

> **小注（215 → 213 的由来，可追溯性）**：早期排查中出现的 **215** 是 `measure_webkit.mjs` 的**简化卡片（无边框）**量得的图片框尺寸；真实 `.photo-card` 带 **1px 边框**，因此在固定列宽 **215px** 下实际图片框 = **215 − 2×1px = 213 CSS px**（DPR=2 时供给 213×2 = **426**）。§2.1 与本 PRD 其余各节的供给尺寸均已统一为 **213 / 426**。

### 2.2 验收标准（必须可量化）

**参考环境（与排查报告一致，固定不变）**：3440×1440 显示器，`UI Looks like 3440×1440`（DPR=1），视口 1212px；样本沿用 `evaluation/preview-resolution/sample.py` 定义的唯一样本，且必须覆盖构图多样性（**横构图 4 张 + 竖构图 4 张**）。

**基准口径（重要，先读）**

- 本节所有 lapvar / MSE↓理想 / 过冲 均为**真实 WebKit 渲染**实测值（权威值），由真实 `ensure_display_asset` 产出。
- **A3 / B3 的基准是「真实旧链路（供 512）」，不是「理想供给」。** 原稿阈值（A3 ≤2.0 / 改善 ≥10 倍；B3 ≤0.8 / ≥3 倍）是基于「从**原图**派生的理想供给」校准的（当时 MSE 0.54），而架构出于成本考虑（不解码原图，HEIC 单张 1655ms）选择**从 512 缩略图派生**，两者叠加后**结构性不可达**，故按主理人裁定改值。
- 该不可达量的构成：**约 4.43 来自「走 512 中间层」**，其余来自 JPEG 再编码（已改用 **q95 4:4:4** 压低；同一链路用 q90 4:2:0 时 MSE 为 19.08，q95 4:4:4 后为 7.50）。
- 实现落定值说明：固定列宽 **215px**、真实卡片含 **1px 边框**，故图片框 = **215 − 2×1px = 213 CSS px**；对应 DPR=1 供 **213** / DPR=2 供 **426**（213×2）。§2.1 与本节已统一为同一口径（不再存在 215 / 430 的供给表述）。

4. **门禁**：`./verify-change-set.sh` 必须 EXIT=0（见 §2.3）。

**已知限制（本轮不修，仅记录）**

1. **非整数 DPR（如 1.5）无法精确 1:1**：WebKit 把列宽取整使图片框为 214 CSS px，此时 `round(213×1.5)=320 ≠ 321`，差 1px。**本 PRD 的精确匹配范围只覆盖 DPR=1 / DPR=2。**
2. **竖构图 + DPR=2 字节放大**：见上文 C1 已知限制，本轮验收放行。

### 2.3 硬约束与门禁影响（实现必须满足）

1. **不得改动现有 512px 分析缩略图**（同 P0-4），新增显示资产与分析缩略图**分开**。
2. **冻结门禁 `verify-change-set.sh`**：`tests/` 与 `models/` 除 `AUTHORIZED_FROZEN` 外必须与上游逐字节一致；`differ` 集合必须精确等于 `EXPECTED_DIFFER`；`added` 集合必须精确等于 `EXPECTED_ADDED`；`web/` 下的改动必须**同时**登记进 `EXPECTED_DIFFER` 与 `AUTHORIZED_WEB`。
   - 落地时必须核对白名单：例如改动 `web/css/base.css`（P0-1 的落点，**当前不在两份清单内**）需同时加入 `EXPECTED_DIFFER` 与 `AUTHORIZED_WEB`；新增后端模块/新增 `deliverables/` 目录需登记 `EXPECTED_ADDED`。**任何白名单变更都须附理由注释。**
3. **本 PRD 文件本身**（`deliverables/preview-sharpness/PRD.md`）是新目录，会被门禁判为 `added`，需一并登记进 `EXPECTED_ADDED`，否则门禁会失败（见 §4 待确认问题 Q1）。
4. **用户运行副本在 `/Applications/Cullumi.app`，重建 `dist/` 不会自动更新它**——交付说明中必须提示「验证前先同步/重装到运行副本」，否则用户看到的仍是旧渲染。

### 2.4 UI / 交互设计要点

- 视觉与交互**外观不变**（卡片尺寸系列保持 ~215px 量级，网格仍自适应列数、仍随窗口重排），仅改变「列宽是否固定」与「图片按精确尺寸供给」。
- 固定列宽后余量由 `justify-content: space-between` 吸收，避免右侧出现突兀空白带。
- `loading="lazy"` 等现有行为保持不变；`object-fit: contain` 保持不变。

## 3. 范围边界（明确「不做」）

以下方向**已实测排除，本需求一律不做**：

1. **提高 512px 上限**（如 1024/2048）：DPR=1 屏上收益为 **0%**（512 vs 2048 只差 0.05%），且 `512` 焊死在 `analysis_version()` 与 `NIQE_VERSION` 上，改动会触发全库重新分析并失效 NIQE 基线，代价极大。
2. **改 JPEG 质量 / 采样**：屏上差异仅 **0.09%**。
3. **只把网格列宽改成整数**（仅此而已、不改供给）：整数盒与小数盒渲染结果**完全相同**（都是 1163.0），不解决匹配问题。
4. **优化 `draft()` 预缩**：该环节屏上损失 100.0%，无损失可言。
5. **粗粒度 `srcset` 阶梯**（只有 256/512 之类候选）：会让浏览器挑到 256（倍率 1.19），清晰度 1091.8 **低于**当前基线，**做错方向会让观感变差**。
6. **`image-rendering: high-quality`**：WebKit 实测 effective 仍为 `auto`，无任何效果。
7. （默认）**不改 `image-rendering` 为 `-webkit-optimize-contrast`**：属走样而非还原，需单独评估（见 P2-3）。
8. **不重构照片分析管线**、**不动 `/api/photo` 链路**：报告已确认该库全 JPEG，`display_preview` 那条 2560px 路径对全 JPEG 图库是死代码；本需求不借机改动它，避免扩大变更面。

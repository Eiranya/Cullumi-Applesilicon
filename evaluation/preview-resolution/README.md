# 图片预览分辨率偏低：逐环节排查报告

排查对象：Cullumi macOS 版照片库卡片（`.gallery` 里的缩略图）。
结论先行：**这不是「像素不够」，而是「屏幕上的物理像素本来就少」+「浏览器缩放比理想重采样差」**。
512px 缩略图上限、JPEG 质量、采样格式三项在当前显示尺寸下都不是可见原因。

所有数字由本目录脚本实测生成（脚本只读，不改照片、不改数据库、不改工作区源码）。

---

## 一、结论摘要

| 环节 | 是否是「看着糊」的原因 | 关键实测 |
|---|---|---|
| ① 源文件本身的分辨率 | **否** | 库内 694 张全部 7008×4672 = **32.741 MP**，无低分辨率素材 |
| ② 预览图的生成与缩放 | **否（在当前显示尺寸下）** | 磁盘缩略图长边全部 = 512px；去掉 512 上限后屏上结果**完全不变** |
| ③ 压缩与采样设置 | **否** | q86 4:2:0 → q95 4:4:4，屏上清晰度 1481.6 → 1482.9（**+0.09%**） |
| ④ 显示尺寸与设备像素比 | **是（主因）** | 卡片图片区仅 **215×143 设备像素**（DPR=1）；供给 512 与显示框**对不上**，浏览器被迫以 BICUBIC 级滤波器缩 2.38 倍 |

一句话版本：**卡片在 DPR=1 的屏幕上只有 215×143 个像素可用，而应用喂给它 512px——
不是喂得太少，是尺寸对不上。** 让浏览器去缩 2.38 倍，它那个 BICUBIC 级滤波器
就吃掉了约 18% 的锐度。实测**把供给尺寸改成正好等于显示框，清晰度 +11.5%、保真度 39 倍**。

## 二、实测数据

### 环节 1：源文件分辨率

```
照片总数 694（.jpg 694）
尺寸分布 7008x4672 ×262 / 4672x7008 ×432
像素      min = max = 32.741 MP
状态      active 423 / quarantined 271
```

源图有 32.7 MP，远超任何显示需求。**这一环直接排除。**

### 环节 2：缩略图的生成与缩放逻辑

生成路径在 `cullumi/media.py:analyze_photo()`：

```python
image, taken = open_image(path, (512, 512))   # JPEG 走 draft() DCT 域预缩
preview.thumbnail((512, 512), Image.Resampling.LANCZOS)
preview.save(temporary, "JPEG", quality=86, optimize=True)
```

磁盘上 694 个缩略图的实测分布：

```
341x512 ×432 / 512x341 ×262     最大长边 = 512
```

即 **512px 上限被执行得很严格**。

**端到端损失链**（关键方法：把每个环节的产物都送进**同一个 215px 显示盒**再测清晰度。
LapVariance 是尺度相关的，在各自原生分辨率上直接比较没有意义）：

| 环节 | 原生尺寸 | 屏上 lapvar | 相对源图 |
|---|---|---|---|
| 源文件（原始解码） | 7008×4672 | 1355.9 | 100.0% |
| ① `draft()` DCT 预缩后 | 876×584 | 1355.4 | 100.0% |
| ② LANCZOS 收到 512 长边 | 512×341 | 1479.8 | 109.1% |
| ③ JPEG q86 4:2:0 落盘（= 实际所用） | 512×341 | 1481.6 | 109.3% |
| ③' 编码 q95 4:4:4（其余不变） | 512×341 | 1482.9 | 109.4% |
| ④ 去掉 512 上限（原图直落显示盒） | 7008×4672 | 1355.9 | 100.0% |

**读法**：从源图到磁盘缩略图，屏上清晰度不但没有下降，反而略升（109.3%）。
原因是两级下采样（7008→512→215）比一步到位（7008→215）保留了更多中频。
**512px 上限没有造成可测的屏上损失。**

磁盘缩略图与「全解码后理想 LANCZOS 512」的差距也极小：

```
on_disk_vs_ideal512_ratio = 0.992     （清晰度比 99.2%）
draft 路径 vs 理想 512 的 MSE = 0.678  （几乎为 0）
```

**这一环也不是主因**——前提是显示盒只有 215 设备像素（见环节 4）。

### 环节 3：压缩与采样设置

解析 SOF 标记得到的实际采样格式：

```
磁盘缩略图  SOF=0xC0  采样=4:2:0
源图        SOF=0xC0  采样=4:2:2
```

在同一张 512 图上只改编码参数：

| 编码 | vs 理想 512 的 MSE |
|---|---|
| q86 4:2:0（产品当前） | 10.768 |
| q95 4:2:0 | 3.862 |
| q95 4:4:4 | 2.703 |

在 512 这个尺度上，q86 4:2:0 确实比 q95 4:4:4 差了约 4 倍 MSE。
**但换算到屏上几乎完全消失**：1481.6 → 1482.9，差 0.09%。
原因同上——215px 的显示盒根本承载不了这些高频差异。

**这一环影响可忽略。**

### 环节 4：显示尺寸与设备像素比 —— 主因

先确认显示环境：

```
显示器   3440 x 1440（UWQHD）
UI 缩放  "UI Looks like 3440 x 1440"   → devicePixelRatio = 1
截图     1712 x 1120（1:1 抓取，无 2x 像素重复）
```

在真实 WebKit 中复现同一段卡片 CSS，量到的图片框：

```
视口 1212px  →  列宽 215.1875px（非整数）
图片框 cssBox = 215.19 x 161.39 CSS px
natural = 512 x 341
DPR=1：需要 215 设备像素，过采样 2.38 倍
DPR=2：需要 430 设备像素，过采样 1.19 倍
```

**决定性对照：把用户截图里那张真实卡片，与同一张缩略图的各种缩放结果比清晰度。**

| 路径 | 屏上 lapvar |
|---|---|
| 屏上实测（应用真实渲染） | **1876.4** |
| 同一张 512 缩略图 + BICUBIC | 1851.9 ← 最接近 |
| 同一张 512 缩略图 + LANCZOS | 2294.6 |
| 同一张 512 缩略图 + BILINEAR | 1179.3 |
| 同一张 512 缩略图 + BOX | 2190.9 |
| 原图 7008 → 显示尺寸 LANCZOS（理论上限） | 2355.0 |

**分解这次损失**：

```
理论上限（原图）                2355.0
  └─ 512px 上限的代价           -60.4   （占 2.6%）
     同一张 512 能做到的最好     2294.6
       └─ 浏览器缩放的代价       -418.2  （占 17.8%）
          屏上实际               1876.4
```

**约 87% 的锐度损失发生在浏览器把 512px 缩进 215px 盒这一步**，而不是图片管线。

交叉对照（逐像素比对，按各自渲染尺寸，避免多加一道缩放抹平差异）：

| WebKit 渲染 | 最接近的 PIL 算法 |
|---|---|
| 默认（`image-rendering: auto`）DPR=1 | **BICUBIC** |
| 默认 DPR=2 | **BICUBIC** |
| `-webkit-optimize-contrast` DPR=1 | **NEAREST** |
| `-webkit-optimize-contrast` DPR=2 | **NEAREST** |

与「理想下采样」的保真度：

| 变体 | lapvar | MSE↓理想 | 边缘过冲↓ |
|---|---|---|---|
| PIL LANCZOS | 1481.6 | 4.47 | 1.59 |
| PIL BICUBIC | 1192.0 | 4.84 | 1.07 |
| **WebKit 默认** | **1163.0** | **23.19** | **1.03** |
| WebKit `-webkit-optimize-contrast` | 2444.9 | 45.45 | 3.42 |

**注意最后一行**：`-webkit-optimize-contrast` 把 lapvar 从 1163 拉到 2444.9（2.1 倍），
但交叉对照显示它实际是**最近邻**行为，MSE 反而从 23.19 恶化到 45.45，边缘过冲从 1.03 升到 3.42。
**这是走样，不是还原**——它看起来"更锐"，但不是更真实。

### 源尺寸扫描：源再大也没用

把 128 / 213 / 256 / 341 / 426 / 512 / 1024 / 2048 各尺寸的源，渲染进同一个固定盒：

| 源尺寸 | DPR=1 屏上 lapvar | DPR=2 屏上 lapvar |
|---|---|---|
| 128 | 942.3 | 333.9 |
| 213 | 1264.4 | 429.5 |
| 256 | 1486.4 | 457.0 |
| 341 | 1570.9 | 510.3 |
| 426 | 1585.1 | 598.1 |
| **512（当前）** | **1590.2** | **694.4** |
| 1024 | 1589.1 | 743.9 |
| 2048 | 1589.4 | 742.1 |

DPR=1 下 256px 之后曲线就走平了，**512 与 2048 的屏上清晰度只差 0.05%**。
**把缩略图上限从 512 提到 1024/2048，在当前显示环境下屏上收益为零。**

## 三、如何判断问题出在哪一环节

按下面顺序走，每一步都能把范围砍掉一半。全部可在开发者工具 + 一段 Python 里完成。

**第 0 步：先确认这台机器到底需要多少像素**

```js
const img = document.querySelector('.thumb img');
console.log(img.naturalWidth, img.clientWidth, devicePixelRatio,
            img.clientWidth * devicePixelRatio);
```

判定：
- `naturalWidth` **远大于** `clientWidth × DPR` → 源像素过剩，问题不在源，往下走第 3 步
- `naturalWidth` **小于** `clientWidth × DPR` → 源像素不足，属于「生成上限」环节

本机结果：`512 vs 215`，过采样 2.38 倍 → **源像素过剩，生成环节无辜**。

**第 1 步：源文件本身**

```bash
sqlite3 ~/Library/Application\ Support/Cullumi/projects/*/project.db \
  "SELECT width, height, count(*) FROM photos GROUP BY 1,2"
```
本机：全部 7008×4672（32.7 MP）。有低分辨率素材才会在这一步暴露。

**第 2 步：磁盘上的缩略图是否达标**

```python
from PIL import Image
from pathlib import Path
d = Path.home()/'Library/Application Support/Cullumi/projects/<项目id>/thumbs'
from collections import Counter
print(Counter(f"{Image.open(p).size}" for p in list(d.glob('*.jpg'))[:50]))
```
若尺寸明显小于设计上限（512），说明缩放逻辑出错；
若尺寸达标但与「全解码后理想缩放」差很多，说明 `draft()` 预缩过头。
本机两者都正常（比例 0.992）。

**第 3 步：把这台机器的 DPR 和盒子尺寸钉死**

```js
console.log(getComputedStyle(img).imageRendering);  // 默认应为 auto
console.log(img.getBoundingClientRect());           // 看是不是小数
```
本机：`auto`，215.19×161.39（小数）。
（**实测结论**：小数盒本身不损失清晰度——整数 215px 盒与 215.19px 盒渲染结果 lapvar 完全相同，都是 1163.0。
所以"非整数列宽导致重采样变糊"这个假设**不成立**，不要往这个方向优化。）

**第 4 步：判定是不是浏览器缩放造成的**

把屏上截取的卡片，与同一张缩略图经各算法缩放的版本比清晰度：

```python
# lapvar(屏上卡片) 与 lapvar(512→LANCZOS / BICUBIC / BILINEAR) 对比
```
- 屏上 ≈ LANCZOS → 浏览器缩放没问题，回去查源
- 屏上 ≈ BILINEAR 或更低 → 浏览器缩放在拖后腿（本机情况，屏上 1876 落在 BICUBIC 1851.9 附近）
- 屏上明显低于所有算法 → 中间还有别的环节在丢东西

**第 5 步：确认浏览器真实使用的算法**

用真实 WebKit 渲染同一张图，与 PIL 各算法逐像素比 MSE，取最小值：
本机结果是 **BICUBIC**（DPR=1 与 DPR=2 一致）。

> **务必按各自渲染尺寸比对**。DPR=2 的渲染图是 430×286 设备像素，
> 若先把它缩到 215 再比，等于多加一道 LANCZOS，会把算法差异抹平，
> 让所有候选看起来都像 LANCZOS。

## 四、优化方向

按**实测收益**排序，并标出代价。

### 1. 接受或拒绝 `image-rendering`（唯一能改变屏上锐度的 CSS 手段）

```
image-rendering: -webkit-optimize-contrast;   /* 实测等效 crisp-edges */
```

- 收益：屏上 lapvar **1163.0 → 2444.9**（2.1 倍），肉眼观感明显"更实"
- 代价：实测等价于**最近邻**，MSE↓理想 23.19 → 45.45，边缘过冲 1.03 → 3.42
- 结论：**这是取舍，不是免费提升**。对以浏览为主的缩略图网格可以考虑；
  但如果用户会放大查看，走样会被放大得很明显。建议先在少量卡片上试看再定。

> 注意：`image-rendering: high-quality` 在 WebKit 上实测 effective 仍是 `auto`，**不产生任何效果**，不要指望它。

### 2. ★ 让供给尺寸精确匹配显示框（真正的解法）

这是唯一能**同时**提升清晰度与保真度的改动，也是本次排查的主结论。

实测：倍率 1.00 时 DPR=1 清晰度 +11.5%、保真度 39 倍；DPR=2 清晰度 +23.9%、保真度 7.4 倍。

实施要点（顺序即重要性）：

1. **显示框尺寸必须可预测。** 当前 `grid-template-columns: repeat(auto-fill, minmax(210px, 1fr))`
   在 1fr 分配后得到 218.33px（默认窗口）/ 215.19px（1212px 视口）/ ~221px（最大化）等
   **随窗口变化的值**，无法据此供给固定尺寸的图。
   两种做法：

   - **A. 固定列宽**：`repeat(auto-fill, 215px)` + `justify-content: space-between`
     （空隙吸收余量）。图片框恒为 215 CSS px → DPR=1 供给 215、DPR=2 供给 430。
     改动最小，且是确定性的。
   - **B. 前端量测**：`ResizeObserver` 量出每张卡片实际宽度，按取整后的尺寸请求
     （`/api/thumb?...&w=215`）。保持流式布局，但需要后端支持按尺寸生成 + 缓存。

2. **用 `srcset` + `sizes` 交给浏览器挑**（配合 A 或 B）：

   ```html
   <img src="…&w=215"
        srcset="…&w=215 215w, …&w=430 430w, …&w=512 512w"
        sizes="215px">
   ```

3. **不要只做「阶梯式 srcset」而不解决尺寸可预测性。** 若候选只能是
   256/512 这种粗粒度，浏览器会挑 256（倍率 1.19），实测清晰度 **1091.8，反而比现在的 1216.5 更低**。
   **做错方向会让观感变差。**

4. **新增的显示资产必须与现有的 512 分析缩略图分开。** 那张 512 同时是
   NIQE 与 sharpness 指标的输入、并参与 `analysis_version` 缓存指纹与
   `NIQE_VERSION` 基线。**不要动它**，另存一套显示用资产。

### 3. 提高 512 上限：**当前显示环境下不要做**

- DPR=1 实测收益 **0%**（512 → 2048 屏上差 0.05%）
- 真正的问题不是"512 太小"，而是"512 和显示框对不上"——提高上限并不解决匹配问题
- 代价极大：`512` 同时焊死在 `analysis_version()`（`rgb512-v1` / `raw-preview512-v2`）
  与 `NIQE_VERSION` 上，改动会触发**全库重新分析**，且会使既有 NIQE 基线失效
- 若将来要做，必须作为**独立一轮**，同时重录 NIQE 黄金基线

### 4. 不要做的方向（已实测排除）

- **改 JPEG 质量 / 采样**：屏上差异 0.09%
- **把网格列宽改成整数**（仅此而已，不改供给）：整数盒与小数盒渲染结果完全相同
- **优化 `draft()` 预缩**：该环节屏上损失 100.0%，无损失可言
- **粗粒度 srcset 阶梯**：会让观感变差（见上）

### 供给侧 A/B：按显示尺寸供给 vs 当前固定 512（★ 决定解法的那次实测）

前面「源尺寸扫描」只比了 256 和 512（两者都不是 1.0 倍），会出现
「lapvar 说 512 更锐、MSE 说 256 更保真」的矛盾。
把**正好等于显示框**的尺寸也放进来，矛盾立刻消失：

**DPR=1（显示框需 215 设备像素）**

| 供给 | 下采样倍率 | lapvar | MSE↓理想 | 边缘过冲 |
|---|---|---|---|---|
| **215** | **1.00** | **1355.9** | **0.54** | 1.53 |
| 216 | 1.00 | 812.0 | 21.87 | 1.47 |
| 256 | 1.19 | 1091.8 | 5.82 | 1.50 |
| 341 | 1.58 | 1194.5 | 9.44 | 1.00 |
| 430 | 2.00 | 1203.5 | 16.01 | 0.95 |
| 512（当前） | 2.38 | 1216.5 | 20.85 | 0.72 |

**DPR=2（显示框需 430 设备像素）**

| 供给 | 下采样倍率 | lapvar | MSE↓理想 | 边缘过冲 |
|---|---|---|---|---|
| 341 | 0.79 | 290.6 | 21.06 | 0.99 |
| **430** | **1.00** | **616.7** | **0.36** | 2.15 |
| 512（当前） | 1.19 | 497.7 | 2.67 | 1.59 |

**结论：倍率 1.00 时两个指标同时最优，而且是压倒性的。**

- DPR=1：供给 215 vs 当前 512 → 清晰度 **+11.5%**，保真度 **39 倍**
- DPR=2：供给 430 vs 当前 512 → 清晰度 **+23.9%**，保真度 **7.4 倍**

原因很直接：**倍率 1.00 时浏览器根本不做重采样**，屏上显示的就是服务端
用 LANCZOS 生成的那批像素——浏览器那个 BICUBIC 级滤波器直接被绕开了。

这也是本次排查最重要的结论：**问题不在「给多少像素」，而在「给的像素数
和显示框对不上」**。512 不是太小，是**尺寸不匹配**。

> 注意 216 那一行：只差 1px 就让 lapvar 掉到 812（比 215 低 40%），
> 说明「接近但不等于」比「差得远」更糟——非整数倍率会触发浏览器的
> 中间相位重采样。**目标必须是精确匹配，不是"差不多"。**

## 五、本次排查踩到的坑（可复用）

1. **两条图片链路必须分清。**
   `/api/thumb` 给的是磁盘上的 512 JPEG；`/api/photo` 因为
   `DISPLAY_PREVIEW_EXTENSIONS` 不含 `.jpg`，会把**原始 7008px 文件原样发出**。
   本库里 `display-*` 预览缓存文件数 = **0**，即 `display_preview` 这条 2560px 路径
   对全 JPEG 图库完全是死代码。排查时若拿错链路，结论会完全反过来。

2. **LapVariance 是尺度相关的，跨分辨率直接比没有意义。**
   同一张图放大或缩小都会改变数值。必须先把各环节产物缩进**同一个显示盒**再比。

3. **lapvar 会奖励走样。**
   最近邻下采样产生的高频伪影能把 lapvar 拉得很高（2444.9），但 MSE 和边缘过冲同时恶化。
   **只看 lapvar 会得出"越锐越好"的错误结论**，必须同时看 MSE↓理想与边缘过冲。

4. **★ 样本错配会静默产生"看起来很合理"的错误结论。**
   本次曾用 DSC02017 渲染、却拿 DSC02554 当比对基准。两张照片尺寸、格式、EXIF 结构完全一样，
   文件层面的任何校验都发现不了，症状只是「MSE 大得离谱」（约 9500），
   很容易被误读成「浏览器缩得极差」。
   **对策：样本路径只允许有一个定义处**（`sample.py`），各脚本一律导入，并带 `self_check()` 自证。

5. **验证手段本身也要被验证。**
   「内容区裁剪」若裁错（把留边当成内容），也会让 MSE 被背景主导而失去意义。
   本次即因为比较的是「图片 + 大片纯色背景」而得到过一版无意义的 ~14000 数值。
